Executive Note

This document is the technical companion to the five-page Vision Memo. The memo is the strategy; this is the implementation footing. Every claim in the memo's Two engines, one stack section can be traced to a specific subsystem, interface, or training signal here. Read this if you want to know exactly what gets built, in what order, what it costs, where the latency comes from, and where the risk lives.

Two design choices anchor everything below. (1) Two technical lineages compose, not compete — implicit multimodal embeddings (Lineage B, MOON3.0 pattern) for recall and cross-lingual fuzzy match, plus explicit knowledge graphs (Lineage A, AliCoCo / AliCoCo2 / COSMO pattern) for precision, constraints, and explainability. Industrial e-commerce converged on this pattern over five years[3]; Prime Video should adopt it, not re-invent it. (2) Both engines run from Year 1 — building the foundation without a customer-facing consumer means you cannot tell whether you built the right foundation. A real Y1 conversational MVP is the only thing that can tell you what to optimize for in Y2's fully agentic phase.

§1 Two Technical Lineages — implicit embedding + explicit KG

Both lineages compose; neither replaces the other.

Industrial e-commerce AI has, over the past five years, converged on a layered architecture in which two formerly-rival research traditions are used together, not in competition. The first — implicit multimodal embeddings — provides recall, cross-lingual fuzzy match, and graceful semantic degradation under typos and paraphrase. The second — explicit constraint-aware knowledge graphs — provides precision, explainability, and the architectural location for safety constraints. The Prime Video Search & Assistant architecture takes both.

Lineage B · implicit multimodal embedding with reasoning
continuous, dense, high-recall semantic match

Before producing the embedding, the model first generates structured product attributes (a "thinking step"). 256-dim representation outperforms 4096-dim baseline. GRPO reward shaping + FIRE-style residuals to preserve fine-grained signal. Reasoning-aware multimodal title encoder (Bet 01). Same paradigm: before producing the embedding, generate structured Reasoning Attributes — Genre / Mood / Visual style / Pace / Audience age / Sensitive content. 256 dimensions per title. Single investment serves search retrieval, recsys candidates, and Assistant grounding — three downstream consumers from one offline pipeline.

Why one lineage alone fails — three structural weaknesses

A V1 architecture that builds only the embedding side leaves three gaps unfilled. (1) No interpretable "why this" answer. An embedding-based ranker can return Tumble Leaf for "blue fox cartoon" — but it cannot say why. The KG can: "a character named Fig is a blue fox; stop-motion; rated 3+." This is exactly what Ask Prime needs to render a grounded response. (2) No safety mechanism for context-dependent recommendations. "Thriller → exciting" is true for adults and harmful for children. Pure embedding similarity does not encode this; AliCoCo2's quadruple does — and constraint c is precisely the dimension Bet 05's evaluation framework weights asymmetrically. (3) No long-tail / cold-start path. When a new MGM original launches, behavioral signal is zero. Behavior-trained embeddings degrade. A KG with attribute and constraint edges (genre, themes, cast, comparable shows) lets Ask Prime tell the truth from minute one.

The 2.0 thesis

Search and Assistant are the two product surfaces. Embeddings (B) and the Viewing Intent KG (A) are the two technical foundations. Both surfaces consume both foundations. The Catalog Intelligence Layer is where they meet.

§2 Catalog Intelligence Layer — internals

Three subsystems, three interfaces, one substrate.

The CIL is a piece of infrastructure, not a product feature. Every active Prime Video surface — Search, Ask Prime, Recsys, X-Ray, Sports, Originals discovery — reads from the same three derived assets, produced offline and exposed through three surface-agnostic interfaces. This is the architectural step that turns Bets 01 and 02 from one-off projects into a platform.

§3 Search Path — sub-200ms hybrid retrieval

Four stages, four retrievers, never returns zero.

The Search Path serves the FETCH and simple FIND traffic — roughly 90% of search volume. End-to-end latency target is ~200ms p95, which forces every component into a tight budget. The path is structured as four sequential stages with parallelism inside Stage 2.

Stage 1

Query Encoding + Rewriting

Cross-lingual encoder (256-dim, shared with catalog) + KG-aware query rewriting (e.g. "blue fox cartoon" → {Tumble Leaf, stop-motion preschool, Fig the fox, kids 3-6}) + spell correction.

Stage 2

Hybrid Retrieval (parallel)

4 retrievers run concurrently — each returns top-50 — fused by Reciprocal Rank Fusion (RRF). RRF is score-agnostic; appropriate for heterogeneous sources.

Stage 3

Multi-objective Ranking

From ~100 candidates → final 10. Weighted value model: relevance · engagement · diversity · novelty · business · safety. Safety is a hard constraint, not a weight.

Stage 4

OOC Detection + Fallback

Never return zero. Below confidence threshold θ_OOC (per-intent learned), fall back to nearest-neighbor + KG scenario expansion: "we don't have X, but try Y, Z, W."

Stage 2 detail — four-source hybrid (most peers run two)

Source Tech Catches Status Lexical (BM25) inverted index over title / cast / director, edge-n-grams for type-ahead FETCH (~50% of traffic, e.g. "The Boys") V1 ✓ Dense ANN CIL 256-dim embedding · HNSW / FAISS / OpenSearch ANN index FIND — semantic match, "blue fox cartoon" → Tumble Leaf ★ V2.0 KG-faceted graph query over CIL Asset 2 (scenario tags) + Asset 3 (constraint edges) scenario queries: "Saturday morning kids", "comfort movie" ★ V2.0 External Web via Bedrock or Brave Search MCP, triggered only when internal recall confidence is low user can't recall title; out-of-catalog query — direct Tumble Leaf fix ★ V2.2

Combination: final_score = ∑ wᵢ × normᵢ(scoreᵢ), subject to constraint c. MMR is then applied on the top-k to enforce diversity. Weights are learned per-locale and per-intent through long-window A/B (60-90 day cohorts) — short-window A/B is misleading because novelty effects inflate w₂ artificially (a lesson from Bing Generative SERP V1: +6% at 14 days collapsed to under +1% at 45 days).

①
4-source Hybrid

BM25 + Dense + KG + Web with RRF. Most peers run 2-source; we recall ~2× more.

Solves: FETCH and FIND simultaneously plus the OOC ~13% tail.

②
Constraint-aware Ranking

Safety enters as hard constraint c, not soft weight. AliCoCo2 quadruples consumed directly.

Solves: family-mode safety, spoiler avoidance, parental control reliability.

③
Calibrated OOC + Fallback

Never returns zero. Calibrated confidence (not raw score) gates fallback into NN + KG expansion.

Solves: the 13% null-result rate documented in SIGIR 2019.[1]

§4 Assistant Path — agentic orchestrator

A single ReAct loop with a good tool catalog.

Through 2025-2026 the agent-orchestrator design space crystallised into roughly four families: multi-agent fan-out (CrewAI, AutoGen, LangGraph multi-agent), explicit DAG (LangGraph graph mode), single ReAct loop (Claude Agent SDK pattern), and tree search (LATS). For Prime Video, the choice is single ReAct loop. Anthropic's own 2025 research on effective agents found that for most use cases a single reactive loop with a rich tool catalog outperforms multi-agent on latency, cost, and debuggability[4]. Our orchestrator is not the innovation; the tool catalog is.

Why not the alternatives — paradigm comparison

ParadigmCore ideaFit for PV Assistant
Multi-agent fan-outDecompose to specialist agents in parallel; orchestrator mergesBad fit. Coordination cost (token / latency / debug) exceeds benefit for EXPLORE queries; one tool-using agent suffices.
Explicit DAGState machine + typed edges defines control flowPartial fit. Good for stable transactional flows (subscribe-flow); too rigid for open dialogue.
★ Single ReAct loopOne model + while-loop: reason → tool_use → tool_result → repeatOur choice. Simple control flow + rich tool catalog. The Anthropic-validated default for production agents in 2025-2026.
Tree search (LATS)Explore multiple trajectories, pick bestBad fit. ~10× latency penalty; PV queries rarely need search-style planning.

  • cross_amazon_lookup(query) Kindle / Audible / Music — consent-gated, off by default · ~100ms
  • imdb_freshness(title) latest reviews, trends, momentum · ~80ms
  • live_sports_state(team) calls existing NBA Key Moments agent · ~150ms
C. Action (side-effects · strict permission gate)~10% of calls

  • subscribe(channel) third-party purchase: explicit confirm + price display, irreversible

D. Memory & State (3-tier)~10% of calls
  • recall_session(turns?) short-term in-context · free
  • recall_preferences() mid-term stated prefs in DynamoDB · user-editable
  • recall_trajectory() long-term viewing history · RUEL sequence model (existing)
  • save_preference(pref) writes only after explicit user approval
Key engineering decision

Tool Search, not Pre-loaded Tool Schemas

Inlining all 14 tool schemas into every prompt costs ~3,000 tokens per turn and — worse — distracts the model: it must re-scan all 14 every decision. Claude Code validated a better pattern: load only tool names (~200 tokens) into context; let the model call search_tool(intent) when it needs a specific schema. We adopt this pattern verbatim, including for our own tools, since it is especially well-suited to MCP-style server contexts.

§5 COSMO-LM — distilling a 7B serving model

Why distill — three independent binding reasons.

The COSMO-LM is not a chatbot. It is a domain-specific judge-and-generator, called millions of times per day from the offline KG-edge pipeline. It does two narrow tasks: (a) edge generation — given a (query, watched_title) pair, emit candidate ⟨s,p,o,c⟩ quadruples; (b) edge scoring — given a candidate quadruple, emit five 0-1 scores (completeness, relevance, informativeness, plausibility, typicality). The task is narrow but the call volume is enormous, which forces the model to be small, cheap, low-latency, and locally hosted. Three independent reasons make distillation a hard requirement, not a preference.

ReasonArgumentMagnitude
① Cost ~10M calls/day × ~1000 tok in/out at current Bedrock Claude prices ≈ $50K/day = ~$18M/year. Distilled 7B on Inferentia2: stable-state ~$1.5M/year. COSMO paper documents a ~20× inference-cost reduction post-distillation. ~12× saving
② Latency Bedrock Claude API median ~600ms, p99 ~2s (network + queue + inference). Inferentia2-served 7B: p99 ~80ms. Online KG lookup SLA is sub-50ms — Bedrock cannot meet this, so distillation is a hard requirement. ~25× p99
③ Sovereignty Search-watch behavior is Amazon first-party data. Sending it across the Bedrock boundary (even within AWS) requires substantially heavier compliance and governance. A locally-distilled 7B keeps the data inside Amazon's network boundary — a non-negotiable for legal and privacy review. compliance gate

Training pipeline · 4 stages. Stage 1 Bedrock Claude Sonnet (teacher) generates ~3M candidate quadruples from sampled search-watch logs. Stage 2 three-layer filter — rule (perplexity, dedup, blocklist), similarity (no tautology), human verification (~30K samples, 18 catalog domains). Stage 3 SFT on LLaMA-3.1 7B / Qwen 7B with the verified set + augmented synthetic instructions; 5-task multi-task training; 8× A100 or Trainium for ~3 days. Stage 4 (optional) DPO/GRPO over preference pairs for borderline alignment. Production: Inferentia2 + vLLM, async cache, daily SageMaker retrain.

§6 Evaluation Framework — the cross-cutting moat

Four evaluations that gate every layer.

Bet 05 (Evaluation Infrastructure) consumes ~30% of headcount. This is the bet that makes the other four shippable safely — the one that prevents a Fallout S2 incident. Four cross-cutting evaluations, run continuously, gate releases at every layer.

EvaluationWhat it measuresWhy it gates everything
RAG Triad (1) groundedness · (2) context relevance · (3) answer relevance — the three RAG quality axes Hallucinations are blocked at the response layer, not just retrieval.
Asymmetric Loss weighted error rates where spoiler / age-rating / safety violations cost asymmetrically more than missed recommendations "First do no harm" made mathematical. A 0.95-NDCG model that ships one spoiler is rejected.
Constraint-Conditional Eval AliCoCo2-style ⟨query, c, expected_safe, gold⟩ four-tuples, per-locale judge panels with calibrated correlation Safety tested as conditions, not averages. Family-mode failure ≠ aggregate pass.
Behavior Simulator 60-90 day holdout cohort + counterfactual session simulator predicting LTV impact before rollout Catches the Bing-generative-SERP failure mode (14d looks great, 45d truth is ~zero).

No model — embedding, ranking, KG generator, or full Assistant — ships without passing all four. This is what "evaluation as moat" means in practice: a structural, organizational guarantee that quality is not shipped by judgment alone.
